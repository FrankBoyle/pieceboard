# Pieceboard data formats

Pieceboard is an alpha. Its documented compact formats retain their `ui-sheet/` identifiers for compatibility. These formats are the public interchange boundary, with shipped [JSON Schema contracts and compatibility rules](schema.md). The full report schema describes the current producer; older alpha reports may need regeneration. Consumers should tolerate additional fields, inspect `format`, and reject unsupported versions. Internal JavaScript functions are not a stable public API. Do not infer a clean result from missing data.

## Full report

`pieceboard scan` writes `ui-sheet.json` with `format: "ui-sheet/v1"` alongside `index.html`. It contains source inventory items, definitions, usages, warnings and, for captured scans, per-page observations and findings. It can embed real screenshots and source-derived text or paths. It is intended for local use and can be large; review it before sharing. Observation source evidence is labeled `likely`, `manual`, `instrumented`, or `unresolved`. A `manual` link is a user's configured assertion; an opt-in `instrumented` link matches a page marker's file, line, column, tag, and SHA-256 fingerprint to selected local source. Page markers can be forged, and none of these labels proves what revision a site runs. Regenerate older reports to include new evidence.

An opt-in `--responsive` capture adds `responsiveAudit` (`ui-sheet/responsive-pages-v1`). Each selected route contains per-viewport coverage, bounded browser measurements, candidate findings, concrete suggestions, and optional masked PNG previews. Findings include the tested viewport width, CSS selector, document coordinates, and optionally a likely source location or computed styles from Chromium DevTools. `previewIndex` identifies a viewport capture; a preview can be missing because of capture or size limits. Conventional `#/...` and `#!/...` router paths are retained so inspected views can be distinguished; URL queries and hash-route parameters are omitted. Route paths, selectors, screenshots and the surrounding report can still contain private information and must be reviewed before sharing. Findings are heuristics, and `observed` only means the supported checks ran within their limits on that captured state.

`pieceboard add-previews` keeps supplied screenshots separate from observed browser captures. A supplied preview may carry `captureMetadata` with `role`, `school`, `viewportWidth`, `viewportHeight`, `capturedAt`, `screenshotSha256`, and `servedSha`. Missing context remains `null`; the image SHA-256 is computed from the supplied bytes. A supplied image hash must match those bytes. `servedSha` is a user-supplied, independently checked website revision, never inferred from the scanned checkout's `sourceRevision`. The report shows both contexts where present and retains the `provided screenshot; source link selected manually` method. A source anchor must already exist on the selected inventory item, but that check does not prove the image depicts the item or that the source revision was deployed.

CLI scans also write `.ui-sheet-scan.json` with `format: "ui-sheet/scan-status-v1"`, a run ID and completion status. The report's `scanRunId` must match a completed status for verified coverage. The temporary `.ui-sheet-scan.lock` prevents concurrent scans to one output directory; if interrupted, it remains until the user verifies the scan is no longer running and removes the lock. A failed scan makes `check` exit 2; a failure during report writing can leave incomplete output. Copy the completion record with the JSON when preserving a report. Missing records are unverified, and argument-parsing failures before a scan starts cannot update a record; workflow steps must also stop when the scan command fails.

HTML/PHP and JSX/TSX element usages can include a one-based `column` as well as `line`. This keeps identical markup on the same line as separate recorded occurrences; other source references may not have a column.

When `inventoryClasses` rules apply, a source usage can include `element.inventoryTypes` with the configured class/type pairs. A matching captured example can have `classification: "configured UI class"`. These labels are user-supplied inventory hints; they do not make non-native elements eligible for the native-button consistency analysis.

## Compact agent and CI output

Captured reports with explicit `layoutChecks` include `layoutAudit` (`ui-sheet/layout-pages-v1`). Each `ui-sheet/layout-v1` page records scope and rule results with `passed`, `finding`, or `incomplete` status. Measurements are bounded scalar values; previews remain separate optional image objects. Manual sources are configured assertions. A print-media page is browser print-preview evidence, not a checked PDF.

`ui-sheet check-layout REPORT --json` returns `ui-sheet/layout-check-v1`: completion status, source-warning count, coverage, aggregate counts, page contexts, and image-free results with preview-availability flags. Runtime validation rejects contradictory counts and unsupported shapes. Partial/unverified evidence never becomes observed coverage. A structured error uses `ui-sheet/error-v1` with `LAYOUT_CHECK_FAILED`. This command is separate from the appearance and source-token checks; use the relevant commands for each configured workflow.

When `check --json` cannot read or check a report, it exits 2 and emits `ui-sheet/error-v1` with `error.code: "CHECK_FAILED"` and a human-readable message. A source-only inventory has no rendered consistency analysis and therefore produces that error; use `catalog` for its source references or `check-tokens` for explicit source token approvals. `check-tokens --json` failures use the same error format with `TOKEN_CHECK_FAILED`. Other CLI commands retain their documented error text.

Source scans also record `tokenSource` with `format: "ui-sheet/token-source-v1"`: attempted CSS `files` and their parse status, plus all selected custom-property `declarations`. Each declaration includes token name, parser value, importance, file, one-based line/column, and full outer-to-inner rule/at-rule context. The existing inventory item's `value` remains its first discovered value for compatibility; it is not an effective value across all themes.

`ui-sheet tokens REPORT` returns `ui-sheet/tokens-v1`, with `sourceStatus`, completion status, bounded entries and stable scope IDs. `ui-sheet token-baseline` stores a `ui-sheet/token-baselines-v1` approval file. `ui-sheet check-tokens REPORT --file FILE --json` returns `ui-sheet/token-check-v1`, with all approved scopes classified as matched, changed, missing, ambiguous, or unscanned. Approval identity excludes source line and value while retaining file, token name, and complete context. A file absent from the selected scan is unscanned rather than a proven removed declaration. These checks do not resolve the CSS cascade or token aliases. See [token contracts](token-contracts.md).

`ui-sheet catalog REPORT` returns `ui-sheet/catalog-v1`: a filtered set of inventory `entries`, with `total`, `truncated`, source references, and `previewAvailable`. Usages are limited; request an item with `--id` for a larger but still bounded set. This output omits image data and does not guarantee a complete dependency graph.

`ui-sheet appearances REPORT --page 1` returns `ui-sheet/appearances-v1`: page and scope, observed button style values, occurrence counts, a representative observation ID, and possible source evidence. The output omits screenshots and may be truncated. Observation IDs are meaningful within the selected page and report; do not treat them as permanent component identifiers.

`ui-sheet locations REPORT --family NAME` returns `ui-sheet/locations-v1`: matching observed button occurrences across the selected pages, including page scope, group, source-confidence clues, and preview availability. `total` and `truncated` describe the bounded result. It omits screenshots and does not account for unvisited pages or hidden states.

`ui-sheet check REPORT --json` returns `ui-sheet/check-v1`. Its main fields are:

- `result`: `findings`, `no-findings`, or `insufficient-evidence`. With no actionable findings, partial or insufficient coverage yields `insufficient-evidence`.
- `coverage`: `observed`, `partial`, or `insufficient`; this applies only to the selected pages and eligible controls.
- `scanStatus`: `completed` when the report matches a completed run record, or `unverified` when no status record is present. Unverified runs have partial or insufficient coverage. A failed, active, interrupted, invalid, or mismatched record causes the check to fail.
- `actionable`, `totalFindings`, and `findings`: counts and individual evidence. Each finding includes its inferred or approved reference, source evidence, review status, and whether it has a source anchor.
- `pages`: route, viewport, detected theme, capture pixel ratio, browser, comparison identity version, counts, and representative preview coverage. Older reports can have missing context; reports predating configurable density used 2×.
- Page counts include `possiblyBlocked` for excluded buttons whose in-viewport hit tests reached another element, and `visibilityUnverified` for eligible buttons whose obstruction was not checked. Missing counts or either nonzero count make coverage incomplete. These tests cannot detect every visual obstruction.
- Buttons with image-based or unsupported background layers are counted in `missingStyle` and excluded from comparison; their background URLs are not retained in measured button styles. This does not redact other report fields or screenshots. Reports using older comparison identities have incomplete coverage.
- When `instrumentedSources` is enabled, each page reports eligible, matched, missing, and invalid-or-overridden marker counts. Missing, invalid, or missing summary metadata makes coverage incomplete. Instrumentation settings must agree when reports are compared.
- `sourceWarnings`: number of source-scan warnings, or `null` when that metadata is missing. Either warnings or missing metadata make coverage partial when there is otherwise comparable evidence. Warning paths and messages are omitted from the compact output.
- `sourceRevision`: enclosing Git context when it tracks at least one scanned source file, including `trackedSourceFiles` and `scannedSourceFiles` counts. A partial count means some scanned files are not tracked in that checkout. This is not proof of deployment.
- `baselines` and `decisions`: optional summaries of matched and unmatched entries when those files were supplied. A stale decision must not be assumed to apply.
- `crossPage`: present for an opt-in cross-page scan, with comparison identity, coverage and group counts, including pages with incomplete button visibility or style evidence. Cross-page findings are included in `findings` and the overall actionable count.
- `elementPages`: present when explicit `elementGroups` were captured, with per-page state-aware configured-family counts and preview coverage. Their findings are included in the same actionable totals; absent data is not an implicit check of those families.
- `elementBaselines`: applied and unmatched configured-element approval counts when a separate element baseline file was supplied.
- `comparison`: present only with `--previous`, with new source-anchored finding IDs and an explicit incomplete status when evidence is insufficient.

`check` is report-only by default. `--fail-on-findings` exits 1 for actionable findings. `--fail-on-new` requires `--previous` and exits 1 for new actionable findings, or 2 for incomplete comparison evidence. `--strict-coverage` exits 2 for incomplete coverage; invalid or incompatible input also exits 2. Comparing reports requires the same cross-page setting and identity version. Output omits screenshots, but source paths and review reasons may still be sensitive.

## Review decisions and approved appearances

Decision files use `ui-sheet/decisions-v1` and contain `findingId`, `status`, `reason`, and an optional `recordedAt`. Decisions apply only to a unique, source-anchored matching finding. A unique static ID matched in both selected source and rendered page can keep a finding identity across line moves within the same file when the scan has no warnings; manually linked and other inferred evidence remains line-based. Instrumented anchors include the source column and file fingerprint, so any change to that file makes the decision stale. Changes in route, viewport, theme, capture pixel ratio, group, measured style, file or element ID can make a decision stale. Reusing an ID for a different control can carry a decision forward, so review after repurposing elements. The visual report can import an existing file and download a merged file; queued changes are not automatically written back. The current finding identity versions are `ui-sheet/button-finding-v6` and `ui-sheet/cross-page-finding-v5`; regenerate older reports before comparing them and review decisions whose IDs become stale.

Baseline files use `ui-sheet/baselines-v4` and contain approved measured button styles for a particular viewport, detected theme, capture pixel ratio, and stable group. A missing `scope.pixelRatio` means 2×. A route-scoped baseline applies to one route; an explicitly selected cross-page baseline uses `scope.url: "*"` and applies to the named group and variant across selected pages. They include a reason and optional likely, manually linked, or instrumented source evidence, but not screenshots. An approved appearance is a reference chosen by a person, not proof that all other appearances are errors. Unmatched baselines are reported.

Version 1 button baselines lack measurements for every border side, versions 1 and 2 lack gradient/text-style measurements, and versions 1–3 lack opacity/filter measurements. Element baseline version 1 also lacks opacity/filter measurements. They cannot be automatically upgraded without guessing. Preserve the old file, capture a fresh report without it, and reapprove appearances into a new current file. Older reports can still be viewed, but regenerate them before a current comparison or approval; changed finding identities require review of saved decisions.

New captured reports can include `approval` templates on observed appearances. The visual report can queue a page or eligible cross-page template, add a reason, import existing baseline rules, and download a merged file. It does not write back to the imported file or apply the result automatically. The next scan validates imported rules. Visual approval is disabled for masked or unavailable previews and duplicate page scopes; the CLI remains available for a separately verified appearance.

These formats are local files, not an authorization to upload project information. Screenshot masks affect captured pixels only; they do not redact report text or source information.
