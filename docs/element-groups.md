# Explicit element comparisons

Configured element comparison is an experimental addition to the native button check. A project supplies CSS selectors, a family, a UI category and, when needed, a deliberate variant. Only selected elements are measured. UI categories are inputs, dropdowns, selectors, tabs, headers, sidebars, navigation, headings and text. Classification is a project assertion; a selector does not establish a design-system component definition.

The capture integration supplies a canonical description of each element's observed semantic state. Comparisons keep family, variant, category, native tag, native input type and state separate. A selected tab is therefore not automatically compared with an unselected tab. Missing state evidence excludes an element and makes coverage incomplete. The scanner must not record field values or ordinary page copy as state.

`analyzeElementConsistency` returns `ui-sheet/elements-v1` with comparison identity `ui-sheet/element-finding-v2`. The result includes the capture scope, counted observations, appearances, possible differences, source evidence and coverage. Observation IDs use the native tag and its document index, such as `input:2`. The capture and report integration provide genuine images separately; this engine never invents a visual.

The comparison uses the same normalized style properties as native buttons: colors, supported gradients, opacity, supported CSS filters, typography, border sides, corner radii, padding and shadow. It does not compare every possible rendered property, dimensions, descendants, ancestor effects or widget behavior. Image-based backgrounds and unsupported resource filters are excluded; their URLs are not kept in measured styles. Screenshots and other report fields still need review before sharing.

Without an approved reference, at least three comparable occurrences are required. One repeated appearance must account for more than half of its group. Alternative appearances, including repeated deviations, become possible outliers. Ties and samples without a majority remain incomplete evidence. Only a singleton outlier can receive one persistent source anchor; use occurrence/source lookup for repeated deviations. A common appearance can be wrong, and an uncommon one can be intentional.

Approve an actual observed reference through `ui-sheet element-baseline REPORT --file ui-sheet.elements.json --observation input:0 --reason "Approved form field"`. Use the observation's native tag and index from the report JSON; `--page N` selects the configured-element page. `--cross-page` approves the same configured group and observed state across selected and future routes, and requires an explicit variant. Apply the separate file with `ui-sheet scan . --capture --element-baseline ui-sheet.elements.json`, or set `"elementBaseline": "ui-sheet.elements.json"` in project configuration. Button and element baseline files are distinct and cannot be substituted.

Element approvals use `ui-sheet/element-baselines-v2`. They bind family, variant, category, native tag/type, observed state, route (or an explicit cross-page scope), viewport, theme, and pixel ratio. A page-specific approval wins over a cross-page approval. Approved references can identify a repeated deviation or a deviation in a small sample; when the approved appearance is absent, the report shows its measured expected values without inventing an image. Approval changes can expire saved review decisions. The file writer validates and merges bounded rules, uses a per-file lock, and refuses unsupported or changed files. A stale lock requires checking that no writer is still running before removing it.

The capture integration measures up to 500 selected elements per page and captures up to 40 representative appearances. The analysis function separately limits retained observations to 5,000 for direct callers. Further selected occurrences are counted as omitted. Hidden and possibly blocked elements are excluded; unverified visibility remains partial evidence. `observed` coverage describes only configured groups and supported properties at the captured state. It does not establish complete app consistency, correct behavior, unobscured pixels, or complete descendant, iframe or shadow-root coverage.

Source evidence remains `likely`, `manual`, `instrumented` or `unresolved`. A uniquely matched static source ID can stabilize a finding across line moves; a reused ID may still refer to a different element. Instrumented identities include their source column and file fingerprint, so changes to that file expire the identity. Neither approach verifies deployment. Regenerate older reports after comparison-identity changes and review saved decisions rather than assuming they still apply.
