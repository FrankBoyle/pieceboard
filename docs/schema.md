# Public JSON contracts

Pieceboard ships JSON Schema 2020-12 definitions in [`schemas/`](../schemas). These describe the current alpha's serialized outputs. They are suitable for validating saved fixtures, building integrations, and detecting incompatible input. They do not make the detector's decisions certain or establish a stable JavaScript API for internal `src/` functions.

## Compatibility rules

Consumers must inspect `format`, tolerate additional object properties, and reject an unsupported format before making decisions. Schemas allow additional properties so a compatible producer can add information. Do not depend on property order, item order, or fields beginning with `_`. Observation IDs identify occurrences within one page of one report; inventory IDs are source clues rather than permanent component identities.

The report schema is a **current producer snapshot**. Earlier alpha reports with the same top-level `ui-sheet/v1` label can lack required measurements or context and therefore fail this snapshot. Keep the original files for reference and regenerate them with the installed version. The HTML viewer may still display older data. Passing the report schema is not a promise that every future alpha accepts that report for comparison.

New integrations should use compact CLI outputs where possible. Their documented formats are the public interchange boundary. Changes that remove required fields or change an existing field's meaning require a new format identifier. Additive fields remain compatible. This policy applies from the checked-in contract onward; it does not retroactively stabilize earlier alpha files. Package version and format version serve different purposes.

Comparison identities are separately versioned. The current identities are `ui-sheet/button-finding-v6`, `ui-sheet/cross-page-finding-v5`, and `ui-sheet/element-finding-v2`. The report schema requires current identities for newly generated analyses. A compact check can legitimately describe an older identity; its coverage remains partial or insufficient. Comparing reports requires matching current identities and compatible route, viewport, theme, browser version, pixel density, instrumentation settings, configured groups, and explicit capture actions. The presence of an ID does not make it a durable source anchor.

Button baseline versions 1–3 and configured-family baseline version 1 lack current measurements. They must not be upgraded by filling guessed values. Preserve the old file, temporarily remove its baseline configuration, capture a fresh report, and approve appearances into a new button version 4 or configured-family version 2 file. Configure that new file afterward. Configured-family baselines include UI type, native tag/type, and semantic state; do not pass button baselines to configured-family analysis. Saved review decisions whose finding identities change become stale and need review; Pieceboard does not automatically transfer the approval.

The [button version 3](../schemas/baselines-v3.schema.json) and [configured-family version 1](../schemas/element-baselines-v1.schema.json) schemas remain historical producer snapshots. They embed their earlier style-property contract and can describe an archived pre-effects file; passing one of those historical schemas does not make the file usable by the current runtime. Current report and baseline schemas require measured `opacity` and `filter` values. Opacity is a numeric string from 0 through 1. Supported filters use computed CSS filter functions or `none`; URL-based and unsupported filters are excluded rather than recorded as complete evidence.

The current button count contract includes `ambiguous` for observations without a strict majority reference. Repeated minority appearances can produce possible-difference findings when a strict majority exists; a repeated alternative is still a review suggestion, not proof of a defect. Button and configured-family `repeatedMinority` counts record repeated inferred minority occurrences considered for comparison; this count alone does not make coverage partial. Consumers must not infer the absence of a difference from frequency alone.

The report's optional `elementConsistency` field contains a versioned page collection. Each page records explicitly selected groups, observed semantic state, normalized styles, appearances, and possible `configured-element-style-outlier` findings. Configured family, variant, UI type, native tag/type, and state identify a comparison group. A tab in its selected state is a different group from an unselected tab. Occurrence IDs use `tag:index` and remain local to one captured page. Configured rules do not establish that all visually similar elements have been discovered.

`ui-sheet/element-appearances-v1` provides one selected page's measured styles, group counts, representative occurrence IDs, source clues, and `previewAvailable` flags. Counts are recomputed from observations rather than copied from saved approval templates. `ui-sheet/element-locations-v1` lists matching observed occurrences with per-occurrence scope and source evidence. Its optional family-variant and UI-type filters appear as `variant` and `type`, with `null` meaning no filter. `scopes` records all selected pages, including pages without a matching occurrence. This is selected-page evidence, not a claim that every use in the application has been found.

Both configured-family query outputs omit screenshot payloads, approval templates, capture-action selectors, and configured selector rules. `totalAppearances` or `total` reports the count before the result limit, while `truncated` indicates a bounded result; arrays contain at most 200 returned entries. `pageCount`, `pagesVisited`, and `matchingPages` describe only the saved capture. `scanStatus` distinguishes completed from unverified reports; failed, active, and mismatched scans are rejected. An unverified query does not become complete evidence because its saved page coverage says `observed`. Use a fresh successful scan and the check contract when making a CI decision or comparing capture contexts.

`ui-sheet/finding-locations-v1` selects one finding by `findingId` and one appearance by `side: "outlier"` or `"common"`. Its `locations` include each matching observed occurrence's page number, URL, local observation ID, group, source evidence, and preview-availability flag. Repeated appearances can therefore lead to several source references even when the finding displays only one representative image. `total` counts occurrences before the limit; `truncated` indicates more recorded locations exist than were returned. Source references can repeat when one source definition renders several occurrences, and unresolved sources remain explicit entries. The output omits screenshot payloads and is bounded to 200 returned locations.

Finding-location queries support current button, configured-family, and cross-page findings. Cross-page matching stays within the finding's rendering and explicit action context. An approved common appearance that was not observed returns zero common locations; the query does not invent a source for that reference. The runtime rejects contradictory occurrence counts, obsolete identities, ambiguous finding IDs, and failed or interrupted scans. Like other occurrence queries, it describes saved observations rather than every possible application use or a deployed source revision.

An optional `scope.actions` array records up to 20 explicit `focus` or `hover` actions with CSS selectors. `scope.elementGroups` records the configured selectors and families. These contexts must agree when reports are compared. An action declaration describes the requested capture context; it is not an instruction for a report consumer to repeat an interaction. The schema permits no click or form-submission action kind. `scope.instrumentedSources` and optional instrumentation counts describe source-marker coverage. The compact check carries configured-family summaries in `elementPages`, configured-family findings in `findings`, and optional approval counts in `elementBaselines`; the full report names those counts `elementBaselineSummary`.

With `check --json`, a command failure emits `{ "format": "ui-sheet/error-v1", "error": { "code": "CHECK_FAILED", "message": "..." } }` and exits with code 2. This is a different contract from `ui-sheet/check-v1`; consumers must branch on `format`. A completed check with findings can emit a valid check object while returning a policy-driven nonzero exit status. A structured error never represents a clean completed check.

## Schema validation and semantic validation

Layout rules produce a separate optional `report.layoutAudit` page collection. Each page records its viewport, screen/print media, browser, color scheme, counts, coverage, and bounded explicit rule results. A result is passed, a finding, or incomplete; measured fields contain scalar geometry/style facts rather than page text. Full results can include a genuine PNG preview. `check-layout` emits a separate image-free compact contract, validates count/status arithmetic and expected-rule shapes, omits unrecognized scope/source fields, and requires a matching completed scan for observed coverage. Errors use `LAYOUT_CHECK_FAILED`. These rules do not change existing appearance baseline identities. See [layout checks](layout-checks.md) for supported evidence and limitations.

Token contracts share scope and declaration definitions in [token-source-v1](../schemas/token-source-v1.schema.json). Source evidence records every attempted CSS file's `scanned` or `failed` status, and declarations with exact parser values, importance, source locations, and full enclosing context. The compact listing exposes `sourceStatus: "missing"` for legacy reports without that evidence; an empty list alone cannot establish that no tokens exist. Baseline scopes use file, token name, and context; IDs remain stable across line moves. Runtime validation verifies their hashes and rejects duplicate scopes. Approval requires completed, unambiguous target evidence.

The separate `check-tokens` command checks a source-only scan. Its output counts `matched`, `changed`, `missing`, `ambiguous`, and `unscanned` approved scopes, with approved/current values and source locations. Missing metadata, unscanned files, and ambiguous scopes do not become clean results. `check-tokens --json` errors use `ui-sheet/error-v1` with `TOKEN_CHECK_FAILED`. Token checks compare saved source declarations rather than the CSS cascade, runtime component values, or edits made after the scan. See [token contracts](token-contracts.md) for the workflow and exit policies.

Schemas validate shape, version labels, types, and selected value limits. Runtime commands still validate relationships that JSON Schema does not express here: recomputed baseline hashes, unique IDs and page scopes, source fingerprints, preview-count arithmetic, eligibility, completion-record/report matching, and whether a saved review applies to the current evidence. Run the commands even after schema validation succeeds.

For a fresh captured report, run its scan successfully and then `ui-sheet check REPORT --json`. Stop when the scan fails. A failed, interrupted, or mismatched scan record causes checking to fail; no record means unverified coverage. A valid `completed` marker is local metadata, not a signature, freshness guarantee, or proof that a deployment matches local code. Schema validation does not verify that marker's run ID against another file.

The scan marker can include optional `pageProgress`; a compact check can expose the same completed metadata, and a report can retain a `scanProgress` copy for display. The object contains `requested` (0–20 pages), sorted unique one-based `observed` and `captured` index arrays, and `active`/`failed` values that are either `null` or `{ "index": 1, "phase": "observe" }` (phase may also be `capture`). These bounded administrative objects reject extra fields; they contain indexes rather than page URLs or content. Runtime validation checks that indexes belong to the requested range, a phase is not simultaneously active and completed, and active and failed work do not coexist. A completed marker requires no active or failed phase and every requested page in the union of observed and captured indexes; scans need not perform both phases. Failed markers retain the failed phase where available. Legacy markers without progress remain supported.

Progress schemas enforce shape, bounds, uniqueness, and the status-specific null fields. Ordering, range relationships to `requested`, completed-page coverage, and agreement with another file are runtime checks. A report's `scanProgress` copy is display context; the matching scan marker remains the source for command completion checks. Do not infer a completed scan merely because one page or phase appears in an array.

`coverage: "observed"` describes comparable eligible groups on selected pages. It does not establish whole-app consistency or complete visibility. `partial` or `insufficient` evidence must not be treated as a clean result. Missing or unsupported style data must remain unknown rather than being replaced by presumed defaults.

Source evidence can be `likely`, `manual`, `instrumented`, or `unresolved`. Manual links are configured assertions. Instrumented links match a page marker to selected local source and a file fingerprint; page markers can be forged. None of these labels proves the deployed revision, an exhaustive dependency graph, or permission to modify another project.

Reports may contain embedded image data, project text, paths, and review reasons. Compact outputs omit image payloads but still contain source details. A schema is not a privacy filter. Review files before sharing them, and keep authentication state outside reports and version control.

## Validation in this repository

`node --test test/schema.test.js` compiles every shipped schema with the development-only Ajv 2020-12 validator. It checks generated source inventory, single-page, cross-page and configured-family analysis, compact outputs, saved baselines, decisions, scan markers, and the CLI's actual JSON failure path. Negative cases cover missing measurements, old versions, invalid source evidence, malformed coverage, unsupported actions, and incomplete configured groups. Ajv is not a runtime dependency and normal scans do not require an online schema service.
